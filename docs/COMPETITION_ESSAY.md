> 项目：[ingredient-radar-skill](https://github.com/Ricardo-100/ingredient-radar-skill)<br>
> [项目报告书](PROJECT_REPORT.md) · [60 秒 Demo](DEMO.md)<br>
> 整理日期：2026-09-28

## 一个标签里，藏着几个不同的问题

“高蛋白”是食品包装上很醒目的信息，但它不足以回答一个人当下的选择：想增肌、想控制糖摄入，或者需要避开某种过敏原，关注点会不同。同一份营养表，每 100 g 的数字和一次吃完整包的数字也不同。

成分雷达围绕这些差别展开。它希望让用户先说清目标，再读取标签，最后把结论、数值与出处一起交还给用户。开发过程中，判断能否被核对逐渐成为组织整个流程的中心。

## 把看图与计算分成明确的步骤

目前项目采用 Agent Skill 的形态。具备看图能力的 Agent 负责找到品名、配料表、致敏原提示和营养成分表，并把字段写入 JSON；Python 脚本处理份量换算、规则匹配和结果输出。

这种分工让问题更容易定位。若糖的数值不对，可以追溯抽取记录和原图；若份量不对，可以检查默认整包与手动指定克数的口径；若结论与数字不一致，可以查看规则以及 Agent 和脚本的分歧记录。

文档整理也需要跟上实现。README 明确说明了命令行需要 `--agent-json`，避免读者误以为脚本单独接收一张照片就能识别。对于计算依赖，项目如实写明 Python、Pillow，以及可选的 PyYAML；当前实现没有集成 NVIDIA 软件栈。Agent 使用什么底层硬件，则由运行平台决定。

## 先问目标，也允许不知道

一个容易被忽略的交互是：目标必须由用户选择。增肌、减脂控糖和生酮在项目中是明确输入，过敏忌口也由用户声明。照片提供的是食品信息，不能据此推断用户的身体状况或健康史。

另一个关键选择是保留“未知”。看不清的数字、没有列出的字段，都不应该被填成看似合理的答案。在结构化记录中，`null` 与零有不同含义；不确定内容需要复核。这个约定直接影响后续计算，也决定了系统怎样向用户表达能力边界。

脚本会重算规则。如果 Agent 的初步结论与重算结果不同，输出会留下分歧标记。这让一次交互有机会在形成确定结论之前停下来核对。

## 让一个具体样例讲清楚流程

宣传片使用了仓库里的合成威化棒标签。样例净含量为 60 g，营养表每 100 g 标注糖 32.4 g、能量 466 kcal。按整包折算，脚本输出每份糖 19.4 g、能量 280 kcal；配料里的花生酱和致敏原提示对应花生直接含有的命中。

这个样例同时展示了三个环节：用户选择“减脂控糖”，明确关注“花生”，然后查看按实际份量计算的结果。画面保留了原文与定位区域，观众可以看到判断来自哪里。

为使演示依据清楚，视频使用已有的 Agent 抽取记录进行脚本回放。它展示的是给定这份抽取后的处理链路，不据此宣称 Agent 对所有食品标签都有同样的识别质量。

## 把工程能力变成一分钟里能看懂的内容

本次材料整理和视频制作使用了 AI 编程助手协作。README、镜头结构、动画代码和导出流程在协作中逐步完成，内容依据来自仓库实现、样例和实际脚本输出。

60 秒横屏视频从“高蛋白就适合你吗”切入，接着展示照片、目标和忌口的输入，再呈现每份营养数字与原图证据。操作部分明确标注为 Agent 对话流程示意，避免让观众把动画当作一个已经发布的独立 App。

制作上使用 Remotion 编写可编辑动画，中文语音采用合成旁白，配乐由代码生成。成片经过关键帧、解码和片内项目二维码检查。仓库公开成片、字幕及演示依据；可编辑的制作工程保存在本地，后续修改文字或数据时可以重新导出。

## 公开材料，也公开限制

项目报告与宣传材料需要和实现保持一致。脚本没有网络请求，并不意味着运行它的 Agent 必然在本机离线处理图片；一个样例回放完成，也不等于已经获得新照片识别准确率。这些区别在报告和 Demo 说明中写明，方便读者理解演示覆盖的范围。

下一步值得做的工作是增加不同版式、模糊程度和单位表达的样例，观察真正的新照片输入会在哪些字段上失败，并继续改善原图复核体验。当前项目的价值在于形成了一条可检查的流程：用户说明目标，系统整理标签，计算有输入，结论有出处，不确定之处能够被看见。

希望成分雷达最终留下的，是一种更容易核对的日常信息工具。看完一条结论后，用户仍然知道它来自包装上的哪一行，也知道什么时候应当重新拍照或人工确认。
