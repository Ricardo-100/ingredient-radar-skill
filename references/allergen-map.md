# 过敏原词表与 direct / cross 分级

实现位置：`scripts/allergen_map.py`。本文件说明映射逻辑与边界。

---

## 1. 为什么需要一层映射

致敏原提示原文写法千奇百怪：

```
含花生、含麸质的谷物(小麦)、乳及乳制品、大豆;生产线亦加工坚果。
致敏原信息：含有小麦、大豆及其制品；本生产线同时处理坚果。
ALLERGENS: contains MILK, SOY. May contain traces of TREE NUTS.
```

用户界面上的忌口项却只有六个固定键：花生、乳、麸质、坚果、大豆、鸡蛋。
所以必须有一层**词面 → 标准键**的归一，否则「含麸质的谷物(小麦)」永远匹配不上用户勾的「麸质」。

---

## 2. 标准过敏原键与触发词

| 标准键 | 触发词（命中任一即归入该键） |
|--------|------------------------------|
| `花生` | 花生、groundnut、peanut |
| `乳` | 乳及乳制品、乳制品、乳糖、牛奶、牛乳、奶、酪、milk、dairy、lactose |
| `麸质` | 麸质、含麸质的谷物、小麦、大麦、黑麦、燕麦、gluten、wheat |
| `坚果` | 坚果、核桃、杏仁、榛子、腰果、开心果、夏威夷果、碧根果、松仁、芝麻、nut、tree nut |
| `大豆` | 大豆、黄豆、豆粉、豆制品、soy、soybean |
| `鸡蛋` | 鸡蛋、蛋类、蛋白、蛋黄、egg |
| `鱼` | 鱼、鱼类、鳕鱼、三文鱼、fish |
| `甲壳` | 甲壳、虾、蟹、贝、crustacean、shellfish |

**归不进去的词原样返回**（不丢弃、不改写），保证不因映射表不全而漏报。

---

## 3. direct 与 cross 的分级

| 类型 | 含义 | 判定词 | 呈现 |
|------|------|--------|------|
| `direct` | 配料 / 提示中明确含有 | 「含有」「含」；referring 抽取出的 `allergens` 数组 | 🚫 级别 `bad`，标题「命中 X:直接含」 |
| `cross` | 产线共线、可能含有 | 「生产线」「共线」「同一生产」「同一车间」「可能含有」「交叉污染」「may contain」 | ⚠️ 级别 `warn`，标题「命中 X:可能存在(产线共线)」 |

**为什么必须分级：** 原版 Demo 最关键的产品化细节之一就是避免「一刀切全红」造成告警疲劳。
对极度敏感者，共线风险同样要警告，但它的确定性明显低于直接含——
用同一级别报警，用户很快会学会无视所有告警。

**优先级规则：** 同一过敏原同时出现在 direct 与 cross 数组中时，**按 direct 算**
（更保守，不会把明确的「含花生」降级成「可能含」）。

---

## 4. 兜底扫描

referring 抽取**没有**给出结构化的 `allergens` / `cross_contact` 数组时，
`derive_present()` 会退化为对 `statement` 原文做一次扫描：用 cross 判定词把原文切成
「直接含段」与「共线段」，分别归一。

这条路只是为了在模型抽取失败时不至于完全漏报；正常路径优先相信结构化数组。

---

## 5. 交叉核验的边界

`cross_check()` 只做**词面交集**：

- 用户勾了但产品没有 → 如实报告「未命中」。**这是符合预期的事实陈述，不是漏判。**
  原版 Demo 里产品过敏原只有 5 项、没有鸡蛋，所以勾「鸡蛋」不产生任何告警。
- 用户没勾但产品有 → **不主动报警**。Skill 不替用户决定该关注什么；
  但 `allergens_present` 字段仍完整落进 contract，前端可以展示「本品含以下致敏原」供参考。
- **不做医学判断**：不说「花生过敏者严禁食用」，只说「命中 花生:直接含，请严格避开」，
  并附「过敏务必人工复核原包装」。

---

## 6. 扩展方法

要加过敏原，只改 `ALLERGEN_KEYS` 一处（加键 + 触发词），
如果同时要在界面上暴露给用户勾选，再加进 `scripts/config.py` 的 `ALLERGEN_OPTIONS`。
不需要动 judge.py、不需要动 rules.yaml —— 过敏 flag 的文案模板已经参数化了。
