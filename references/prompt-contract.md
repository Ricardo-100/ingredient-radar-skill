# 提示词契约（grounding / referring / double_check）

**2026-09-25 起第①②步由 Agent 自己看图产出**（见 `agent-mode.md`），
本 skill 不再调用任何外部推理端点，原先的 `scripts/llm_client.py` 与
`scripts/backends/` 整个目录（含 `qwen_vl.py` / `base.py`）已删除。

所以本文的性质变了：**它不再是「发给某个模型的提示词」的说明书，而是契约本身**。
提示词与字段契约的唯一事实来源仍是 `scripts/regions.py`，Agent 照它读图、填
`agent-mode.md` 里的那份 JSON；本文件解释的是**为什么这样设计**，便于后续调参。

消费侧的两处实现：
- `scripts/agent_mode.py::validate()` —— 本地校验 Agent 交上来的 JSON，
  字段缺失 / 类型错误 / 坐标越界都会给出带明文原因的报错（而不是让链路静默出错）；
- `scripts/vision_types.py` —— 坐标回映射与区域裁剪（`box_to_pixels()` / `crop_region()`），
  原先在 `backends/base.py` 里。

> **一条仍然成立的取舍**：契约里「不要编造框」「看不清填 null」「保留图上小数位」这些
> 纪律，是当年写给外部模型的，现在写给 Agent——**一条都没能放松**。
> 因为在场的人换了，失败模式一点没变：多模态模型（不管部署在哪里）定位失败时
> 都会倾向给一个「看起来合理」的框。

## 1. 坐标口径：为什么统一用 0–1000

Qwen-VL 系列的原生 grounding 格式使用 **0–1000 绝对归一化坐标**：

```
<|object_ref_start|>配料表<|object_ref_end|><|object_ref|><|box|>(120,180),(890,340)<|box_end|>
```

本项目不直接消费这个 token 序列，而是要求模型**输出 JSON**、坐标仍按 0–1000：

```json
{"regions":[{"key":"ing","phrase":"配料表","box":[120,180,890,340],"score":0.95,"found":true}]}
```

理由：

1. JSON 比 token 序列好校验（字段缺失、类型错误可以直接发现并拒绝）；
2. 0–1000 与 Qwen-VL 原生口径一致，**不引入二次缩放误差**；
3. 主流 VLM 的 grounding 输出就是 0–1000 归一化坐标，契约天然对齐；
4. 回映射公式极简，任何人都能当场手算：`px = round(v / 1000 * W)`。

回映射实现：`scripts/vision_types.py::box_to_pixels()`。

## 2. Grounding 提示的设计要点

```
只输出 JSON，不要解释文字、markdown 代码块标记
坐标系 0–1000 归一化整数
找不到某个区域 → found=false, box=[0,0,0,0]，不要编造框
score 宁低勿高；看不清填 0.3 以下并把 found 置 false
is_food_label：风景/人像/账单/截图 → false
```

关键取舍：

- **「不要编造框」必须写进去。** 多模态模型在定位失败时倾向于给一个「看起来合理」的框，
  而一个假框会让下游 referring 对着一块空白区域硬抽内容——这是最危险的失败模式。
- **`found` 与 `box` 双保险。** 即便模型嘴硬说 found=true，`box_area_ratio() < 0.0015`
  （面积小于画面的 0.15%）也会被代码判为未定位。宁可漏，不可假。
- **`is_food_label` 是负向用例的第一道闸。** 它让「风景图」在第①步就被拒掉，
  根本进不了 referring，也就不会产出任何成分结论。
- **四个区域一次问完，而不是分四次问。** 单次出四个框可以互相约束位置
  （配料表一定在营养成分表上方），四次独立问会丢这种全局信息，且耗时 ×4。

## 3. Referring 提示：为什么必须裁剪后再抽

这里说的「裁剪」现在是两步：Agent 自己在上下文里看局部（它的等效动作是
把注意力放到那块区域），脚本拿到框后用 `box_to_pixels()` 裁出子图、
放大到宽度 ≥700 px，**再交给 Agent 做第②步的逐字段抽取**。三个原因：

1. **小字会掉。** 营养成分表的「18.6 克」在整图里可能只有十几像素高，
   直接看整图，模型大概率读错或读不出。裁剪 + 放大到宽度 ≥700 px 后准确率明显改善。
   （这条当年是用外部端点实测出来的：整图里读不出的 18.6，裁开放大后读得出来。）
2. **职责隔离。** 模型只看配料表的裁图，就不可能把营养成分表的数字写进配料表字段。
3. **double_check 要复用同一块裁图**，保证「抽的时候看的图」和「核的时候看的图」是同一张。

裁剪实现：`scripts/vision_types.py::crop_region()`，带 4% 外扩
（否则紧贴框线的半行字会被切掉）。

### 字段契约

每个区域一张字段表，见 `regions.py::REFER_SPECS`。三条铁律：

| 铁律 | 为什么 |
|------|--------|
| 数字必须与图上一模一样，保留图上小数位，**不许换算单位** | 任何加工都会让「可点回原图核对」失效 |
| 图上没有的字段填 `null`，**禁止填空字符串 / 0** | `null` 和 `0` 的语义完全不同，后者会污染判定 |
| `legible` 布尔字段单独存在 | 表格数字能否读清，是 `uncertain` 判定的直接输入 |

`ingredients` 字段额外要求「**必须严格保持图上从左到右的原始顺序**」——
因为 GB 7718 的递减排序是糖来源结论的核心证据，顺序被打乱这条证据就没了。

## 4. double_check：三态复核

```
agree       一致，照抄
corrected   不一致，把图上真实值写进 corrections，并给完整 revised JSON
unreadable  模糊/裁切缺失/被遮挡 → 不猜、不补
```

三条设计：

1. **三态而非二态。** 「不认」和「看不清」必须分开。把不可辨的东西硬塞进「不一致」，
   模型会倾向于编一个值填进去；单独给 `unreadable` 才能让它老实说看不清。
2. **禁止因为「看起来不合理」而改值。** 提示里明写「只认图片原文」。
   否则复核会变二次创作：一个看着离谱但图上真是这么印的数字会被「修正」成常见值。
3. **复核失败不让链路崩。** 复核环节出错时记录 `notes` 后放行——复核是增益，
   不是单点故障。Agent 模式下这件事由 Agent 自己把握：填不出 `corrections`
   就照抄原文并在 `uncertain_reasons` 里说明，**不要为了填满字段而猜**。

**关于「开思考」：** 原先由 `IR_THINKING_DOUBLE_CHECK=1` 控制、且是外部端点的
请求参数；2026-09-25 端点删除后该开关随之取消。对数字较真这条纪律没有取消——
它现在体现为 `agent-mode.md` 填表纪律第一条「看不清就填 null，别猜」。

## 5. 结构化输入怎么被校验（原「降级路径」一节）

2026-09-25 之前这一节讲 `llm_client.chat_json()` 的三级降级
（`json_object` 约束 → 花括号配对抠 JSON → 去掉约束再试），
因为那时要保证外部模型吐出的东西能进 `json.loads`。
现在没有模型请求了，**要保证的是 Agent 交上来的人工 JSON 不会把链路带进歧路**，
所以换成 `scripts/agent_mode.py::validate()`：

- 顶层字段逐个按 `_NUMBER_FIELDS` / `_ARRAY_FIELDS` / `_STRING_FIELDS` 校验类型；
- 坐标必须落在 0–1000，越界直接拒（而不是悄悄 clamp 后当成定位成功）；
- `verdict_id` 必须在 `rules.yaml` 里真实存在——**模板会把这些合法 id 一起打出来**
  （`main.py --dump-agent-template`），所以不用凭记忆猜；
- 每条报错都带明文原因，例如「`regions.nut.data.sugar` 要是数字，
  你给的是字符串："32.4 克"」。

三级降级的思想其实留下来了，只是换了个位置：**不再反复请求模型改输出，
而是一次性把 schema 交给人（Agent）照着填**。前者治标、且每次都要花一次网络往返。

## 6. 已知的坑（都踩过）

| 坑 | 现象 | 处理 |
|---|------|------|
| **推理模型的输出分成两半**（历史坑，2026-09-25 前用 Qwen3-35b 时踩的） | `content` 为 `null`，正文全在 `reasoning`；且 reasoning 会把 `max_tokens` 吃光，`finish_reason=length`，拿到的是截断的空壳 | 当时默认传 `chat_template_kwargs.enable_thinking=false`、`_text_of()` 兼容 `reasoning` 兜底、开思考时预算提到 8192。端点虽已删除，**这条坑在未来接任何推理模型时仍然有效** |
| 模型返回 ```json 包裹 | `json.loads` 直接失败 | 花括号配对抠第一个完整 JSON，容忍围栏与前后缀废话。现在这段逻辑由 Agent 侧的 `validate()` 报错替代——人看到报错会自己改格式 |
| 模型用 `phrase` 不用 `key` 返回区域 | 键匹配全部落空，四区全判未定位 | 按 `REGION_BY_KEY[key].phrase` 反查一次 |
| 边缘区域被框线切字 | 抽取缺行 | `crop_region()` 4% 外扩 |
| 打分虚高 | 每个框都是 0.95+ | 提示里写「宁低勿高」；代码 clamp 到 [0,1]，并在 SKILL.md 声明 score 是自报值不可跨模型比较 |
