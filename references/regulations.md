# 法规依据速查（GB 7718 / GB 28050）

本文件是 `scripts/rules.yaml` 与 `scripts/judge.py` 里所有文案的法规出处。
需要引法规依据时直接翻这一页。**以下为通用知识整理，不构成法律意见，具体以现行标准正文为准。**

---

## GB 7718《预包装食品标签通则》

### 配料表的排序是强制要求

配料表必须按**加入量的递减顺序**排列（加入量超过 2% 的配料）。

**这为什么对成分雷达重要：**

静态 Demo 原版的糖来源结论写的是「糖来自配料表前列的「白砂糖 + 麦芽糊精」」，
听起来像主观判断。上升到法规级，它是一条硬证据：

> 「白砂糖」排在配料表第 2 位、「麦芽糊精」排在第 8 位，
> 而 GB 7718 强制要求按加入量递减排序 —— 所以「糖类来源靠前」本身就是可核验的事实。

实现位置：`scripts/judge.py::sugar_ingredients()`，只在配料表**前 10 位**里挑含糖来源，
避免把一个排在 20 位之后的甜味剂说成主要糖源。

### 致敏原的强制标示

GB 7718 要求对含麸质的谷物、甲壳类、鱼、蛋、花生、大豆、乳、坚果等致敏物质进行强制标示。
常见写法：「含有……」「致敏原提示：……」「生产线亦加工……」。

实现位置：`scripts/allergen_map.py`，按词面映射到标准过敏原键，并按
`direct`（明确含有）与 `cross`（产线共线）分级——避免「一刀切全红」造成告警疲劳。

## GB 28050《预包装食品营养标签通则》

### 「0」不等于绝对为 0

| 成分 | 可标注为「0」的条件 |
|------|---------------------|
| 能量 | ≤ 17 kJ / 100 g（或 100 ml） |
| 脂肪 | ≤ 0.5 g / 100 g |
| 饱和脂肪 | ≤ 0.1 g / 100 g |
| 胆固醇 | ≤ 5 mg / 100 g |
| **反式脂肪酸** | **≤ 0.3 g / 100 g** |
| 糖 | ≤ 0.5 g / 100 g |
| 钠 | ≤ 5 mg / 100 g |

**成分雷达的处理：** 反式脂肪 flag 的文案明确写成
「表上标示为 0 g（GB 28050 口径：反式脂肪酸 ≤ 0.3 g/100 g 即可标注为 0，故「标 0」不等于绝对为 0）」，
同时**保留原版「这一点是好的」结论不变**（只是补上置信度说明）。
这是附录 A3 的落地——真实使用中最容易被追问、也最容易被含糊过去的法规细节。

实现位置：`scripts/rules.yaml` → `base_flags.trans_fat.thresholds[0].detail`；
常量 `config.GB_TRANS_ZERO_LIMIT = 0.3`。

### NRV% 口径

GB 28050 要求以 **NRV%（营养素参考值百分比）** 呈现。

| 营养素 | NRV（GB 28050 原值） |
|--------|----------------------|
| 能量 | **8400 kJ**（÷4.184 = 2007.6 kcal，本项目用这个口径） |
| 蛋白质 | 60 g |
| 脂肪 | ≤ 60 g |
| 碳水化合物 | 300 g |
| 钠 | 2000 mg |

**能量这一项最容易搞错：** 国标写的是 **8400 kJ**，不是 8400 kcal。
把它当 kcal 当分母，占比会小 4.184 倍（一份 280 kcal 的威化会报「3.3%」，
实际应是 280 / 2007 ≈ 13.9%）。`config.NRV_ENERGY_KJ = 8400` 存的是国标原值，
`config.NRV_KCAL = NRV_ENERGY_KJ / 4.184 ≈ 2007.6` 才是千卡口径的分母。

**成分雷达的处理：** 钠 flag 并列绝对毫克数与百分比
「钠 192 mg / 份 · 约占钠 NRV(2000 mg) 的 9.6%」，绝对数不如百分比直观。
同时给出 `kcal_nrv_pct` / `protein_nrv_pct` / `fat_nrv_pct` / `carbs_nrv_pct`，方便横向比较不同产品。

**分母有两档（v1.3 起）：** 默认用上表的人口 NRV；用户在 CLI / 网页填了年龄、性别、体重、
身高、活动水平，能量分母就换成 Mifflin-St Jeor × 活动系数算出的「维持当前体重一日所需」
（久坐 ×1.3 / 一般健身 ×1.55 / 高强度 ×1.8）。蛋白 / 脂肪 / 碳水 / 钠仍用人口参考值——
个人化的「你该吃多少」属于饮食处方，不在本 Skill 的机械比对边界内。
契约里的 `daily_reference` 只写分母与活动系数，不写年龄体重原值。

### 营养成分表的标示单位

能量以 **千焦（kJ）** 为强制单位，可同时标示千卡（kcal）。
本项目按图上实际标注单位读取；图上只有 kJ 时由 `serving.resolve_energy()` 按
1 kcal = 4.184 kJ 换算成千卡，并把依据写进 `notes`（例：能量 0 kJ → 0 kcal）。
标签同时给了两个单位时以直给的千卡为准，不做二次换算。

## 其他会直接影响结论的口径

### 净碳水（net carbs）

净碳水 ≈ 总碳水 − 膳食纤维 − 糖醇。

**成分雷达的处理：** 只有当成分表**明确列出了膳食纤维**时才计算净碳水；
否则 `net_carbs_per_100g = null`，生酮 verdict 的文案改为
「碳水约 X g / 份……成分表未提供膳食纤维，净碳水不可知，此处按总碳水从严判断」。

这正是附录 A4 的要求：**原版 keto 文案写「净碳水」但代码取的是总碳水**，
是原版唯一一处口径与措辞不一致。改成按总碳水从严判断并明说，
比硬改数字更站得住——它践行的是 Demo 自己的「不臆测数值」原则。

### 蛋白质「优质来源」阈值

原版内联口径是「≥ 20 g / 份」够得上优质蛋白来源。
本项目把它抽到 `rules.yaml` 的 `reference.good_protein_threshold_g`，
并增加 `metric_below` / `metric_at_least` 分支，让 ≥20 g 的产品得到诚实的好评而不是
永远「名不副实」。同时补附录 A2 的「蛋白质密度」派生量：
`g 蛋白 / 100 kcal`，把「一般」这种主观词变成任何人都能当场验算的数字。

### 方糖换算

原版约定 **1 块方糖 ≈ 4 g 糖**（`config.SUGAR_CUBE_G`）。
这是行业科普常用近似值，非国标；文案统一写「≈ N 块方糖」而不是「= N 块」。
